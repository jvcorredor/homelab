The **Rockingham Homelab** has two compute components: the six-node
Talos Kubernetes cluster (`rockingham`) and the **utility host**, a
hand-installed Proxmox VE machine at `pve.home.arpa`. It is not a
cluster node and not part of the [floor](../): it is where non-cluster
workloads — a scratch VM for testing an OS, a durable service, a build
server — have a home
([ADR-0011](https://github.com/jvcorredor/homelab/blob/main/docs/adr/0011-utility-host.md)).
It follows the cluster's admission rule: installed by hand, and
understood.

## Hardware

| Part | Detail |
|------|--------|
| CPU | 11th Gen Intel Core i5-11600K — 6 cores / 12 threads at 3.9 GHz |
| Memory | 32 GB (31 GiB usable) |
| GPU | NVIDIA GeForce RTX 3060 Ti LHR (GA104) — installed, not passed through |
| System disk | 500 GB WD NVMe (`WDS500G3X0C-00SJG0`) |

The GPU is host-only today: no guest can use it until the firmware
prerequisite for passthrough is met ([below](#what-is-deferred)).

## Identity and access

| Kind | Where |
|------|-------|
| Hostname | `pve.home.arpa` (PVE node name `pve`) |
| Address | `192.168.1.248/24` on `vmbr0`; gateway `192.168.1.1` |
| Uplink | onboard Realtek RTL8125 2.5GbE (`nic0`); Wi-Fi is down and unused |

- **SSH** — `ssh root@192.168.1.248`, key-based. The workstation's key
  is authorized.
- **Web UI** — the Proxmox interface on port `8006`. The host maps
  `pve.home.arpa` to itself, but a workstation resolver usually does not
  know the `.home.arpa` zone, so `https://192.168.1.248:8006` is the
  address that works.
- **API** — the `terraform/proxmox` root talks to the PVE API with a
  least-privilege token; the
  [root's README](https://github.com/jvcorredor/homelab/blob/main/terraform/proxmox/README.md)
  owns it.
- **No remote access** — the host answers on the LAN only. A VPN
  overlay is the future option if access from outside the lab is ever
  needed.

## Install record

Proxmox VE **9.2.18** (kernel `7.0.14-16-pve`) was installed by hand on
the bare machine, EFI-booted, with the `pve-no-subscription` repository
(`/etc/apt/sources.list.d/pve-no-subscription.sources`, Trixie). Two
things from the install are worth remembering:

- The installer pinned the onboard NIC to `nic0` by MAC under
  `/usr/local/lib/systemd/network/` (`50-pmx-nic0.link`), so it keeps
  its identity across kernel updates and device-order changes. An
  additional `nic1` pin targets the Wi-Fi adapter's MAC but is inert —
  `Type=ether` never matches it — so Wi-Fi stays `wlp4s0` and unused.
- The disk was left on the single-disk default layout — no ZFS, no
  RAID — so the storage below is the whole story.

## Storage

One 500 GB NVMe, an EFI partition, and an LVM volume group `pve`:

| Volume | Size | Holds |
|--------|------|-------|
| `/boot/efi` | 1 GB | EFI system partition |
| `pve-root` | 96 GB ext4 | Proxmox VE itself, and the `local` directory datastore |
| `pve-swap` | 8 GB | Swap |
| `pve-data` | ≈338 GB LVM-thin | VM disks and cloud-init drives — the `local-lvm` datastore |

`local` is a directory datastore on the root filesystem; it holds ISO
images, including the Debian cloud image the template was built from, and
the `buildkit-01` cloud-init snippet. Every durable VM disk lives on
`local-lvm`.

## VMs

| ID | Name | State | Spec | Owner |
|----|------|-------|------|-------|
| 200 | `debian-13-template` | stopped template | 2 vCPU · 2 GB RAM · 8 GB disk on `local-lvm` | [`terraform/proxmox/`](https://github.com/jvcorredor/homelab/tree/main/terraform/proxmox) |
| 201 | `buildkit-01` | running | 4 vCPU · 8 GB RAM · 64 GB disk on `local-lvm` | [`terraform/proxmox/`](https://github.com/jvcorredor/homelab/tree/main/terraform/proxmox) |

VM 200 is a Debian 13 (trixie) generic-cloud image: a template, never
started, with no identity or fixed address of its own. Future durable
VMs clone it and take their user, SSH key, and address from cloud-init
at clone time. Durable VMs use IDs in the **2xx** range and are declared
in [`terraform/proxmox/`](https://github.com/jvcorredor/homelab/tree/main/terraform/proxmox);
throwaway VMs use **9xx**, are made with `qm` or the UI, and are absent
from this table by design — they exist to be destroyed
([ADR-0011](https://github.com/jvcorredor/homelab/blob/main/docs/adr/0011-utility-host.md)).

`buildkit-01` is the first tenant: it clones the template and runs
BuildKit for LAN clients over mutual TLS. The client bundle, the pinned
BuildKit release, and the provisioning story live in the
[root's README](https://github.com/jvcorredor/homelab/blob/main/terraform/proxmox/README.md#buildkit-01).

## What is deferred

- **VT-d / GPU passthrough.** Not configured: VT-d is not yet enabled
  on the host, so there are no IOMMU groups and guests are CPU-only.
  The RTX 3060 Ti waits on
  [#244](https://github.com/jvcorredor/homelab/issues/244).

The builder that this page once deferred was earned on 2026-09-13 and
built as VM 201 (`buildkit-01`), recorded in
[ADR-0011](https://github.com/jvcorredor/homelab/blob/main/docs/adr/0011-utility-host.md)
([#253](https://github.com/jvcorredor/homelab/issues/253)).

## Operations

The operating detail lives with the code:
[`terraform/proxmox/README.md`](https://github.com/jvcorredor/homelab/blob/main/terraform/proxmox/README.md)
owns the API token, the `tofu plan`/`apply` workflow, and the clone
pattern for the next durable VM.

The host itself is patched by hand — `apt` against the no-subscription
repository — and nothing scans it or notices when it falls behind;
`tofu plan` is what surfaces drift in a durable VM.
