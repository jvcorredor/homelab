The lab sits on one flat LAN, `192.168.1.0/24`, behind an Optimum
Gateway 6E. The gateway hands out DHCP only in the lower half of the
subnet; everything cluster-related is statically addressed above it.

| `worker-02` | Worker | `192.168.1.242` | |
| `worker-03` | Worker | `192.168.1.243` | |

The Kubernetes API answers on the shared control-plane VIP,
`https://192.168.1.240:6443` — any of the three control planes can serve
it. Every node also exposes the API locally on `localhost:7445`
(KubePrism), so pods do not depend on the VIP being reachable.

Per-node configuration is version-controlled under
[`talos/patches/nodes/`](https://github.com/jvcorredor/homelab/tree/main/talos/patches/nodes),
with the canonical inventory in the
[Talos runbook](https://github.com/jvcorredor/homelab/blob/main/talos/README.md).

## Address plan

| Range | Owner | Purpose |
|-------|-------|---------|
| `192.168.1.11` – `.199` | Optimum Gateway 6E | DHCP leases for everything that is not the cluster |
| `192.168.1.200` – `.230` | Cilium | `CiliumLoadBalancerIPPool` — addresses handed to `Service`s of type `LoadBalancer` |
| `.240` – `.247` | static | the control-plane VIP and the six nodes |

The pool sits between the two other ranges on purpose: below it, DHCP
cannot collide with a service address; above it, the static node range
stays contiguous. The pool is defined in
[`cilium.tf`](https://github.com/jvcorredor/homelab/blob/main/terraform/bootstrap/cilium.tf);
its bounds are variables in
[`variables.tf`](https://github.com/jvcorredor/homelab/blob/main/terraform/bootstrap/variables.tf).

## How a LoadBalancer service gets an address

There is no MetalLB and no separate load-balancer appliance. Cilium runs
the whole path:

<Diagram
  src={lbTraffic}
  wide
  alt="Sequence diagram: the operator applies a LoadBalancer service; Cilium assigns an address from the pool and announces it via ARP from a worker; the gateway forwards traffic to that worker; Cilium delivers it to a backend pod."
  caption="A LoadBalancer service — from apply to traffic."
/>

1. A `Service` of type `LoadBalancer` is applied.
2. Cilium's LB IPAM assigns the next free address from the pool.
3. A **worker** announces the address on the LAN via ARP. The
   `CiliumL2AnnouncementPolicy` excludes control planes on purpose:
   announcing from a control plane risks ARP flapping during a failover.
4. Traffic for that address is delivered through the datapath to a
   backend pod.

Services can opt out of L2 announcement with the label
`homelab.jackhall.dev/l2-announce: "false"` — Cilium still allocates an
address, but no worker answers ARP for it, so it is unreachable from the
LAN by construction. That is the supported way to park a pool address off
the network.
